# kernel-core notes (Venture OS kernel)

Built 2026-11-12 (Fix 8, 2026-11-14: no job queue; one trigger per task, see the last section). 91 kernel operations in 5 catalog files; 1 kernel trigger (question_asked); 17 kernel collections in `1741000000_kernel.js` plus request limits in `1741000001_kernel_limits.js`. Tests: `reference/tests/kernel-core/` (t01 to t07, 340 checks, all passing on empty and seeded scratch databases with the mock bridge). Gate passes on the scratch copy. These notes win over `reference/BUILD_SPEC.md` where they differ.

## Contract changes and additions (read first)

1. **Every write op runs in one tracked transaction.** The dispatcher runs a write handler inside `runInTransaction` through the activity tracker (`lib_activity`): the op is atomic (a throw rolls back every write) and leaves one undo unit; the answer carries `_activity` (also the `X-VO-Activity` header). Ops that call the bridge or the network, or must keep counters through a refusal, declare `track: false` (new catalog field). Inside a tracked op `ctx.app` is the tracker: use `ctx.app.save / delete / find*` as usual; raw SQL writes are not undone; never write through `$app` or `e.app` in a handler.
2. **guide_*.js shape** (SPEC 4.2 wording, made exact): `{ title?, section: string | string[], events?: string[], <trigger>: string | string[] }`. Every other key is the full recipe of the trigger with that name; a recipe list starts with its one-line summary. Every trigger in `events_*.js` `triggers` must have its recipe in the same module's guide, and every recipe must be a trigger's, or `tools/gen.mjs` refuses. The closing data rule is appended to every recipe app.guide serves (Fix 8).
3. **events_*.js keys**: `on, approvals (unused), needsYou, triggers, search, settingsKeys, imports, timeline, today` (Fix 8: `triggers` replaces `jobs` and `asks`). `today: 'lib_x.fn'` is new: fn(ctx) -> `{ key, ... }`, a block of `app.today`. Unknown keys are refused by gen.mjs.
4. **Proposal kinds are open**: any `[a-z][a-z_]+`. Only the promotable kinds of REPORT Table 38 can go auto: `note_fields, merges, asks, map_entries, stage_moves` (`lib_settings.PROMOTABLE`); every other kind always asks. A propose op may add `auto: 'lib_x.fn'` (ctx, params) -> true when its promoted kind may run directly for these params (deals.move: only to Screen). Who sees a proposal: anyone who may run one of its ops (the catalog perm), and its deal when the params carry `deal`.
5. **Propose ops get three kernel params**: `why`, `evidence` (a quote, or JSON `{quote, file, page, url, anchor, message}`), `confidence` (0 to 1). Handlers never see them.
6. **NextItem** adds `module` (filled by the kernel) and an optional `data` object for custom cards. Actions whose op the person may not run are dropped; `pin` is set for confirm ops. Bad items (unknown kind, no key or title, unknown op) are reported in `errors`, never a 5xx. Each action may also carry, passed through unchanged: `done` (the text of the result toast, e.g. 'Passed'), `undo` (`{ op, params }`: the op that reverses it, the toast's Undo; the op must exist), `tone` (`neutral | good | warn | bad`; anything else becomes neutral).
6b. **Outbound draft items** carry `data.edit = { op: 'outbound.update', params: { outbound }, fields: { subject, body } }`: the E key in Focus edits the draft and saves through that op.
7. **Roles**: fields `levels`, `votes` (votes in committee), `own_items` (the scout: sees only what they submitted; `ctx.ownOnly`). Levels per Table 39 are in the migration seed. `funds`: fund metrics, capital aggregates, marks, reserves; `lps`: LP records, commitments, capital accounts, LP letters (principal and analyst have funds view, no lps).
8. **Fund scope**: `members.funds` (JSON list of fund or SPV ids; empty = all). `lib_auth.scope(ctx)` answers it; `ctx.funds` holds it (HR OS `ctx.entities` is gone).
9. **lib_fx** answers objects: `rate(app, from, to, day) -> { rate_e8, day, source } | null`; `avg(app, from, to, fromDay, toDay)`; `convert(app, minor, from, to, day, mode, fromDay) -> { minor, rate_e8, mode, day, from_day, source } | { minor: null, reason, message }`. Rates are `fx_rates.rate_e8`; the period rate is the engines' `lib_eng_kpi.rateFor` and the conversion `lib_eng_core.convertMinor` (coordinator's note). Zones and local days come from `lib_eng_days` (HR OS's table is gone from lib_util).
10. **lib_outbound.approve(ctx, id | { outbound })** sends at once only outside a transaction; called from a tracked module op it marks the message approved and the minute cron sends it. `cc` is not supported (send_gmail has no cc); recipients are `to` only.
11. `pin_vault`, `members` and `roles` changes are never undone (security); nor audit, activity, notifications, proposals, snoozes, the trigger queue. A fired trigger is not undone (Fix 8: the request stays; the record's `agent` state is machinery written with raw SQL).
12. `setup.complete` params: `firm_name, base_currency, zone (default UTC), fund_name, fund_size (major units, optional), fund_vintage (default this year), fund_currency (default base), owner_name, email, password, pin`. Answers `{ token, recovery_code, fund, management, me }`.
13. Kernel events: `entity.created { entity, kind }`, `entity.updated { entity, kind }`, `setup.completed { firm, fund, member }` (Fix 8: job.done, job.failed and job.retried are gone), `outbound.sent` and `outbound.failed { outbound, kind, module, ref_collection, ref_id, deal }`.
14. Realtime topic `vo`, message `{ c: [collections] }`.
15. Extra ops beyond SPEC 4.7: `fx.convert`, `proposals.create`. `pin.verify` answers 200 `{ ok: false, code, attempts_left }` for a wrong PIN.
16. `pocketbase migrate up` boots the hooks too: the kernel's boot work (cron catch-up, asking your AI agent) runs only under `serve`.
17. The scaffold's `1700000000_init_items.js` is deleted and `ops.pb.js` holds no route (HR OS kernel practice).
18. **Deal references are ids or display ids** (D-0001) everywhere the kernel takes one: `lib_auth.dealVisible(ctx, deal)`, proposals (the stored `deal` is the id), `lib_agent.ndaAllowed(app, deal)`, outbound, tasks and comments on `deals`. They resolve through kernel-records' `lib_deals.ref`; new helpers `lib_auth.dealRef(app, ref) -> record | null`, `dealId(app, ref) -> id | ''`, `needDealId(app, ref, param) -> id` (404 naming the param).
20. **Roles that see only their own items** (`own_items`, the scout): `lib_auth.owns(ctx, rec)` is true when the record's `submitted_by`, `member`, `assignee` or `requested_by` is the caller; `recordVisible` answers false for anything they do not own (and for deals). Kernel reads follow it: outbound (their own messages, or about a record they own), proposals (none), questions (the ones they asked), tasks (theirs), activity (their own changes). Modules that list their own records should use `owns` for these roles.
23. (Fix 8: the job queue and its conditional status moves are gone; a record's ask is written once when the trigger fired and once when it landed or was refused.)
22. **`app.batch` (new op, GET, signed)**: `--calls '[{"op":"next.list","params":{}}, ...]'`, at most 12 reads in ONE request; answers `{ results: [{ op, status, data } | { op, status, message, code, data }] }`, each call checked as on its own (permission, params), one failing call does not stop the others, writes and file-streaming reads refused per call. **The frontend should load each page's first reads through it.** Why: every request runs the platform's six JS middlewares (`_system.pb.js` 3, `_a2app.pb.js` 2, `_triggers.pb.js` 1), each holding a pooled runtime, so the default pool of 15 serves about two requests at once and the rest run in throwaway runtimes that load the app's code from scratch. Measured on a fresh merged server (machine at 100% CPU from other builders): ten page-load reads fired together 4.3 to 10.7 s; the same ten as one app.batch 1.2 s. `--hooksPool=120` alone did not help (every runtime still starts cold), and warming the pool at boot cost about a second per runtime per 2 MB of hook code (5 minutes for 10 runtimes under that load), so it was removed.
21. **Kernel task items in Next** (tasks due) carry Snooze (`next.snooze`, until tomorrow 08:00) beside Done, each with `done` and `undo`.
19. **Next is cached per person** in the app store, tagged with the data version and the firm's day, for at most a minute. The version moves after every committed record save or delete (hooks.pb.js) and on `lib_bus.touch(collection)`. **Code that writes with raw SQL must call `lib_bus.touch(collection)` afterwards**, or Next can lag up to a minute. Snoozes are applied per call. Boot builds the lists of members seen in the last 30 days.

## Rules every module builder needs

1. Handlers are `fn(ctx, params)`. `ctx`: `{ e, app, op, spec, actor: 'person'|'agent'|'system', isAgent, member, memberId, name, email, role, roleCode, levels, owner, votes, ownOnly, funds, run, audited, auditInfo, dryRun }`.
2. Errors: `throw u.fail(status, message, code, extra)` (`u = require(`${__hooks}/lib_util.js`)`). Never throw plain strings.
3. Audit: the dispatcher writes one row per write op; give it detail with `lib_audit.note(ctx, { collection, record, summary, before, after })` (the activity unit takes the same summary and target).
4. Require helpers inside functions and memoise them (`let _m = {}; function L(n) { ... }`).
5. A `propose` op is dry-run in a rolled-back transaction before the proposal is stored (`ctx.dryRun` is true): refuse impossible input with a 4xx; keep network and bridge calls out of propose ops.
6. Reads that withhold rows say `hidden: n`.
7. Deals: `lib_auth.dealVisible(ctx, deal)` (record or id): fund scope, then restricted deals for the team (`deal_people.member`, `team` true) and the owner; your AI agent only with `agent_allowed`. `lib_auth.recordVisible(ctx, collection, id)` follows a record's `deal` field. `lib_auth.fundDataVisible(ctx)`: LP data (people: lps view; your AI agent: while `settings.agent_sees_fund_data`).
8. Display ids: `u.nextId(app, 'D', 4)` -> `D-0001` (settings.seq, raw SQL, never rewound by an undo); `u.nextNumber(app, key)`.
9. Days and zones: `u.today(app)`, `u.localNow(app)`, `u.dayOf(app, at)`, `u.atOf(app, day, 'HH:MM')` in the firm's zone (`lib_eng_days`); `u.ppm(p, name)` reads percent text to ppm; `u.e8(p, name)` reads decimals to `_e8`; `u.money(p, name, currency)` major text to minor.
10. Module settings: declare defaults in `events_<module>.js` `settingsKeys: { <key>: { ... } }`; read with `require('lib_settings').module(app, '<key>')`; people change them through `settings.update --modules`. Per-fund settings: `entities.settings[<module>]`.
11. Jobs: declare `jobs: { <kind>: 'guide_<module>.<kind>' }` and put the kind in one trigger of `lib_wake.js` (gen_triggers refuses a kind without one); queue with `lib_jobs.enqueue(app, { kind, ref_collection, ref_id, deal, nda, summary, payload, priority, requested_by | auto })` (a person's id, or an Automatic work key that is on; neither: null and nothing is queued; deduped by kind and ref while wanted; the trigger fires once, see Fix 7). A one-click Ask that needs the module's payload registers `asks: { <kind>: 'lib_x.fn' }` (fn(ctx, { ref_collection, ref_id, note }) -> job view) and the screen calls `jobs.ask`. React to results with `on: { 'job.done': 'lib_x.fn' }` (payload has kind, ref, result) or read them in the module ops your recipe calls. NDA: `lib_jobs.ndaAllowed(app, jobId, dealId)`. A job asked by a person (`jobs.ask`) carries only `payload.ref_collection, ref_id, note, on_request`.
12. Next: `needsYou: 'lib_x.fn'` -> NextItem[] for ctx (SPEC 4.3 shape; `kind` in `verdict, draft, proposal, vote, decision, verify, alert, condition, payment, mark, candidate, note, task, stall`). Use stable keys `<module>:<id>`.
13. Outbound: `lib_outbound.draft(ctx, { kind, module, to, subject, body, attachments: [file ids | {collection, id, field}], ref_collection, ref_id, deal, approver, job })`. The draft appears in Next for editors of `module` (or `approver`); people approve. React with `on: { 'outbound.sent': ... }`.
14. Mail: `lib_mail.search(app, query, max)`, `get(app, id)`, `attachment(app, messageId, attachmentId, filename) -> { ok, path, size }` (saved under `pb_data/mail/<message>/`; load it with kernel-records' `lib_files.fromPath`), `labels(app)`, `answer(res)` (the bridge answer with the 200-with-error check, for calendar calls a module makes itself), `bridgeUp()`.
15. Imports: register `imports: { <target>: { label, perm, fields: [{ key, label, required, type, synonyms }], row: 'lib_x.fn' } }`; `row(ctx, row, info) -> { action: created|updated|skipped, id, message }`; check before writing (a row that throws after writing makes the batch refuse).
16. Search: `search: 'lib_x.fn'` (ctx, q, limit) -> `[{ kind, id, title, subtitle, href, icon }]`.
17. Cron: `cron_<module>.js` `[{ name, schedule, fn: 'lib_x.fn', catchUp }]`, five fields in the firm's zone, fn(app). Use the given app.
18. Tasks for modules: `lib_tasks.open(app, { title, ref_collection, ref_id, deal, assignee, due_day, note })`. Notifications: `lib_notify.notify(app, memberIds, { kind, title, body, link: '#/...', facts, ref })`, `toLevel(app, module, level, n)`.
19. Sealed values (funds): `lib_seal.seal(app, plain)`, `unseal`, `mask(plain)`, `reveal(ctx, sealed, what)` inside a `confirm` op.
20. LPA (entities.lpa): `{ confirmed, mgmt_fee_ppm, fee_basis: committed|invested|net_invested|nav, step_downs: [{ from_year, fee_ppm, basis? }], carry_ppm, waterfall: european|american, hurdle_ppm, pref_compounding: compound|simple (default compound), catch_up_ppm, recycling_cap_ppm, recycling_window_years, gp_commit_ppm, investment_period_years, term_years, extension_years, fee_offset_ppm }`; `lib_entities.validateLpa`, `DEFAULT_LPA` (2% committed, 20% carry, European, no hurdle, `confirmed: false` until a person saves the terms).
21. After copying files into APP run `node tools/gen.mjs` and `node tools/gen_triggers.mjs`.

## Decisions

- Undo guards compare the touched fields' values with their state when the unit ended (not the `updated` stamp), so a run that edits one record twice undoes cleanly newest first; a whole run is one transaction (all or nothing).
- Your AI agent's run: a new run after each trigger fires or after 30 minutes without a write; runs live in the app store (a restart starts a new run).
- Outbound pace: at most 20 sends in any 60 seconds; the rest wait as approved and the minute cron sends them. A message claimed for sending (`sending`) is never sent twice; a failed one can be approved again.
- AI-use disclosure: `ai_chars` and `typed_chars` per message; a person's edit counts the changed middle as typed and removes the replaced share proportionally.
- `exports.all` writes a stored ZIP (JSON per collection, secrets left out, sealed fields dropped) and streams it.
- Rates: Frankfurter first (and its time series for averages), then currency-api; a rate set by a person is never replaced by a fetched one.

## Known gaps

- `exports.all` leaves stored files (decks, documents) out of the ZIP (listed by name in their records).
- Undo of a deletion recreates the record, but PocketBase deleted its stored files with it: a file field comes back pointing at nothing.
- `outbound` has no cc or bcc (Gmail's action takes none).
- A message left `sending` by a crash during the bridge call stays there (never resent); a person can cancel it after five minutes.
- Zones are the engines' 101; a firm elsewhere picks the nearest listed zone.

## Majors fix (2026-11-12, QA M1, M4, M6, UI-02/m1)

1. **M1 draft edit.** Outbound draft Next items keep `data.edit = { op: 'outbound.update', params: { outbound }, fields: { subject, body } }`; the Focus card now saves every changed field through that op, and `outbound.update` takes exactly that (`outbound` plus `subject` and/or `body`; a person's body edit counts as typed text).
2. **UI-02 proposals people can read.** `lib_proposals.line(label, before, after, type, name)` answers `{ name, label, before, after, was }`, or null when nothing really changes (`"3000000.00"` equals `"3000000"`). Types: `text` (default), `money:<CUR>` (major-unit text or numbers, compact "USD 12.5M", full figures when compact would hide the change), `minor:<CUR>`, `ppm`, `e8`, `int`, `number`, `day`, `bool`, `list`. `titleOf(name, fields)` builds "<record name>: <field labels>"; previews may return `ref` (a display id such as D-0019, kept in data, never the title). Fields a preview sends without a label get one from their name; unchanged ones are dropped; `was` (the comparable before value) drives the stale check at accept. `proposals.get` adds `kind_label`, `ref`, `items[].ref`, `fields[].label`. Next proposal items: one neutral chip with the plain kind label, `data.ref`, figures by label, and `pin` on Accept when accepting needs the PIN. Kind labels (`KIND_LABELS`): Merge, Stage move, Deal update, Import, ...; `note_fields` reads Deal, Company or Person update by its op, and "From a meeting note" when your AI agent proposed it while working a `note_review` job (each item stores `via`, the one claimed job kind of the run). **Module builders: build preview lines with `line()`.**
3. **M6 activity.list scope.** The owner sees every entry and everyone sees their own changes. Any other entry needs view rights on a module its op's catalog perm names (LP data through `fundDataVisible`) and a visible record: its deal (restricted deals, fund scope), its fund in scope, an outbound message's module, a job's module (from `events_*.js` jobs; deals work is pipeline) and record; scouts only their own records; a deleted record is judged by the deal and fund in its undo data. Answers `hidden: n` (the runs view too).
4. **M4 PIN for import targets.** New catalog field `pinIf: 'lib_x.fn'` (ctx, params) -> true when this call needs the caller's approval PIN.
