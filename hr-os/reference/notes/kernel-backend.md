Built 2026-11-04. 160 kernel operations in 6 kernel catalog files (the whole app: 717 operations in 41 files). Gate passes on APP. Tests: `reference/tests/kernel-backend/` (t01 to t11, about 370 checks, passing on empty and seeded scratch databases with the delivered country files, the 38 packs and the merged modules). These notes win over `reference/BUILD_SPEC.md` where they differ.

## Rules every module builder needs

1. Handlers are `fn(ctx, params)`. `ctx`: `{ e, app, op, spec, actor: 'person'|'agent'|'system', isAgent, member, memberId, name, email, role, roleCode, levels, owner, teamScope, entities, employeeId, audited, auditInfo, dryRun }`.
2. Audit: the dispatcher writes one audit row for every write op. Give it detail with `lib_audit.note(ctx, { collection, record, summary, before, after })`, or write your own rows with `lib_audit.write(ctx, {...})` (then the dispatcher writes none). Fields ending `_sealed`, `kiosk_code` and secret params never reach the trail; mark a param `secret: true` in the catalog to keep it out.
3. Transactions: `ctx.app.runInTransaction((tx) => { const t = lib_auth.withApp(ctx, tx); ... })` and pass `t` (or `tx`) to every kernel call inside. Never use `ctx.app`, `e.app` or `$app` inside the callback (deadlock; the gate checks `e.app` and `$app`).
4. Require helpers inside function bodies, memoised: `let _m = {}; function L(n) { if (_m[n] === undefined) _m[n] = require(...); return _m[n]; }` (require costs about 2 ms a call).
5. Writes need a credential on the platform: a member token, the page's session cookie (set by `GET /`) or `X-A2App-Token`. `tools/dev/api.mjs` does it and retries PocketBase's 429 answers.
6. Never write collections from the UI; every collection refuses raw API writes (`hooks.pb.js`).
7. After copying files into APP run `node tools/gen.mjs` (routes get the gzip middleware there; `hooks.pb.js` has no `routerUse`).
8. A propose op is run once in a rolled-back transaction before the proposal is stored (`ctx.dryRun` is true then): make the handler fail with a clear 4xx for impossible input, and keep side effects outside the database (emails, HTTP) out of propose ops.

## Catalog (SPEC 3.1) and the extras

- `perm`: `public`, `signed`, `self` (same check as signed; the handler scopes), `<module>:<view|edit|full>`, `admin` (= `admin:full`); alternatives with `|` (`'payroll:view|reports:view'`). Modules: people, time, leave, expenses, payroll, hiring, performance, reports, admin. Your AI agent passes every module perm (it is full on reads); `agent: 'deny'` is the only block, and it is checked before params and the PIN.
- Added by the kernel (do not declare): `pin` (required, secret) on `effect: 'confirm'`; `confirm` (boolean) on destructive ops your AI agent may run; `why` on `agent: 'propose'` ops.
- `operations.json` (what your AI agent's CLI reads): people-only ops show no `pin` param and no required params (so the call reaches the server and gets the 403 with the hand-off) and end with `[People only: hand it over with inbox.route.]`; proposal ops end with `[Proposal (kind).]`.
- Proposal previews: `diff: { collection, id: '<param>', fields: { <param>: '<field>' } }` (records found by id, and employees, employments, entities and org records also by number or name), or `preview: 'lib_x.fn'` returning `{ label, target, fields: [{ name, before, after }], notes, risk }`. A destructive op cannot be `propose`.
- `files: ['field']`: multipart fields; read them with `lib_files.fileParam(ctx, p, 'field', 'path')` (your AI agent passes `--path`).
- gen.mjs refuses: names not `group.verb` ([a-z0-9-]), desc over 400 characters, en or em dashes, missing or non-exported handlers (it loads the lib in Node), bad perms or kinds.
- `frontend/src/app/lib/ops.gen.ts`: `export const OPS = { 'name': { method, effect, perm, agent, destructive? } } as const; export type OpName; export const PIN_OPS: ReadonlySet<OpName>`.
- Group names taken by the kernel: app, setup, countries, search, auth, pin, members, roles, settings, audit, fx, imports, entities, locations, departments, titles, grades, cost-centers, employment-types, calendars, holidays, schedules, people, employments, job, pay, tax, documents, employee-skills, ids, bank, seal, approvals, approval-flows, proposals, questions, agent, inbox, notifications. `questions.*` are questions to your AI agent and `agent.*` (retry, triggers) belongs to `lib_agent` (see "Agent triggers" below); job openings use `openings.*`.

## Module files the kernel discovers

- `events_<module>.js`: `{ on: { '<event>': 'lib_x.fn' | ['lib_x.a', 'lib_x.b'] }, approvals: { <kind>: 'lib_x.fn' }, profileFacts: 'lib_x.fn' }`.
- `guide_<module>.js`: `{ title, rules: [...], triggers: { <trigger>: 'instruction under 1,000 characters' }, recipes: { <trigger>: ['summary', '1) ...'] }, events: ['name { payload }'] }`. `app.guide` shows the index (rules, conventions, modules with their op groups and triggers, one line per recipe); `app.guide --module <m>` the section in full; `--recipe <trigger>` one recipe.
- `cron_<module>.js`: `[{ name, schedule: '*/15 * * * *', fn: 'lib_x.fn' }]`, five fields in UTC, `fn(app)`; the kernel's one minute job runs what matches, each in its own try. Use `lib_util.localNow(app, entityId)` for local hours per entity.
- `data/countries/<cc>.js` and `packs/<code>.js` (files starting with `_` are helpers, not packs).

## Country data shape

`pb/pb_hooks/data/countries/<cc>.js`, file name the lower-case ISO 3166-1 alpha-2 code:

- Required: `code` (upper case, equals the file name), `name`, `currency` (ISO 4217, the pay currency of a new entity), `timezone` (an IANA zone in `lib_util.ZONES`), `date_format` (tokens YYYY MM DD), `week_start` (0 = Sunday), `weekend` (weekdays off, 0 = Sunday), `name_order` (`family_first` | `given_first`).
- Optional: `timezones` (more zones), `fiscal_year_start` (`MM-DD`), `regions` ([{ code, name }], ISO 3166-2 codes without the country prefix: `CA`, `13`, `MH`), `id_types` ([{ code, label, mask: last4|last3|none, pattern }]), `packs` (pack codes a new entity enables), `region_packs` ({ <region>: [codes] }), `bank_formats`, `schedule` ({ days, start, end, break_min }), `employment_types` ([{ code, name, statutory }]; the kernel seeds five generic ones when absent), `leave_types` (read by the leave module), `min_wage` ({ hourly, monthly, currency, note, by_region }), `holidays` ([{ day, name, region: '' or a region code, kind: public|company|optional|observed, half }]), `sources`, `notes`, `filings`.
- Creating an entity copies the holidays (region '' plus the entity's region, every year in the data) into a calendar `<CC>` or `<CC>-<region>`, creates the standard work week and the employment types, enables `packs` plus `region_packs[region]`, and emits `entity.created`. Boot adds years new data brings (only years a calendar was never seeded with).

## Kernel events

`entity.created { entity, country, region }`, `employment.hired { employment, employee, entity, start_day, from_application }` (also for each imported row), `employment.changed { employment, kind: 'job'|'pay'|'tax', record, effective_from, edited }`, `employment.ended { employment, employee, entity, end_day, reason }`, `employee.updated { employee, fields }`, `bank_account.approved { bank_account, employee }`, `member.linked { member, employee }`, and the query event `record.editing { collection, id, employment, effective_from }`: a subscriber returns `{ block: '<reason>' }` to refuse an in-place Edit (payroll: the record was used by a locked run).

13. New ops `jobs.release` (with `note` and `to`) and `inbox.route` (your AI agent only, in-app links, quoted request, dedupe by record); `jobs.next` takes 5 by default; `jobs.done` and `jobs.fail` answer a short `job` (id, kind, status, summary, done_at, result_chars, error), not the payload; `documents.delete` is people only; your AI agent may remove skills it may set.

16. Dates: `auth.me` answers `company.date_format` (tokens YYYY MM DD: the company `date_style` iso, dmy, mdy or ymd, or with `entity` the format of the person's primary entity, else the first), `company.week_start`, `company.home_entity`, and per entity `date_format`, `week_start`, `name_order`; `app.home` adds `date_format` and `week_start`.
14. Proposals are checked before they are stored: an empty call answers 400 `empty_proposal`, an impossible one the handler's own error prefixed "Not proposed:" (404 with close names for an unknown reference).
17. Structured facts (migration `1730000300_kernel_facts.js`): approvals and notifications carry `facts`, search results `facts` next to the plain `subtitle`: `[{ type: day, value } | { type: range, from, to } | { type: money, amount_minor, currency } | { type: state, value } | { type: number, value, unit } | { type: text, value }]`, each with an optional `key` and `label` (`lib_util.facts(list)` checks the shape). Modules pass `facts` to `lib_approvals.open` and `lib_notify.notify`; an approval without facts shows its amount as a money fact; the plain `summary` and `title` stay for the CLI. Search titles no longer hold dates (pay runs: the entity; leave: the person).
18. `setup.countries` rows add `region_packs` and `pack_names` (`{ code: name }` for the country and region packs).
19. New op `pin.verify` (people only): `{ ok: true }`, or 200 `{ ok: false, code: wrong_pin, attempts_left }` (`pin_locked` with `minutes`, `pin_not_set`, `pin_required`); wrong tries still count toward the lock. Confirm ops keep answering 403 `wrong_pin`.
20. Reference resolution (`lib_people.employeeRef`, used by every `employee` and `employment` param): id, number, work email, full name; then one word matches a given, family or preferred name or the first word of the preferred, legal or given name (`Priya`, `Kenji`, `Sam`). One match resolves; several answer 409 `ambiguous` with `data.matches`; none 404 with close names.
21. `locations.list` rows carry `entity_name`; `app.status` has `server: { port, env }`.
22. `pay.update` takes reason `hire` (starting pay; the first pay record of the employment only, else 400 `not_first` with `data.first_day`), matching payroll's `comp_changes` reasons. With no `effective_from`, an Update (pay, job, tax) of an employment with no record of that kind yet is from the first day of work (else today); the proposal preview uses the same day. Update refusals are sentences without field names, each with a code and `data.param`: `before_start` (`data.start_day`), `after_end` (`data.end_day`), `exists` (409, `data.record`), `missing_param` / `invalid_param` for the reason (`data.reasons`), `invalid_amount` (`data.currency`, `data.decimals`), `missing_param` for the amount. The dispatcher's own checks (required params, enums) keep their generic text with `code` and `data.param`.

## Speed and limits

- Boot (`warm()` of `lib_catalog`, `lib_events`, `lib_guide`, `lib_countries`) keeps the completed catalog (whole and one op per key), the event subscriptions, the cron list, the guide sections and the country and pack indexes in the app store, shared by every runtime, and loads the kernel libraries once so the pool reuses their compiled code.
- First requests after a restart: `people.get` 2,337, 912 and 10,999 ms on cold runtimes before, 33 to 248 ms after; `entities.list` 198 to 209 ms before, 14 ms after; boot to healthy 23.8 s before, 6.9 to 11.9 s after (machine under load). 8 parallel cold `setup.status`: 385 to 407 ms (server 311 to 338) before, 489 to 519 ms (server 192 to 231) after, then 147 to 159 ms; 8 parallel `people.get` 1,251 to 1,282 ms before, 497 to 516 ms after.
- Rate limits (`1730000200_kernel_limits.js`, per client address per minute; the relay's forwarded address counts): `/api/ops/` 1,800; `POST /api/ops/auth/login` and `accept-invite` 30, `auth/recover` 10; `/api/ops/setup/` 300; `/api/ops/kiosk/` 600, `POST /api/ops/kiosk/punch` 60; `*:auth` 240; `/api/collections/` 1,200; the platform's `/api/_console` 120 and `/api/_coverage` 600.
- `people.hire` (40 hires in a row on a loaded machine): server p50 274 to 296 ms, p95 1.0 to 2.0 s. The kernel part averages 90 to 100 ms (one write fewer per new person now, no country file load); the event subscribers add `lib_lifecycle.onHire` 169 ms on average (max 1.1 s), `lib_leave.onHired` 31 ms and `lib_hiring_offers.onHired` 14 ms. Every record save also runs the kernel's JS record hooks (realtime marks), each in a pooled runtime.

## Known gaps and notes for the coordinator

- Platform (runner.py): each request runs the six JS `routerUse` middlewares of the system hooks, each holding a pooled runtime until the request ends, so PocketBase's default pool of 15 serves about two requests at once on warm runtimes and the rest get throwaway cold ones. 8 parallel requests in repeated waves: slowest per wave 110 to 550 ms with `--hooksPool=15`, 40 to 190 ms with `--hooksPool=120`. Pass `--hooksPool=60` or more in runner.py's serve command, or fold the system middlewares into one. `tools/dev/serve.sh` takes `PB_SERVE_FLAGS="--hooksPool=60"`.
- `app/agent_app/manager.py` (export_project `skip_names`) does not skip `.seal-key`: an exported zip carries the key (pb_data is not exported; backups cover pb_data only, so backups never hold it). Restoring a backup on another machine needs the key copied by hand.
- Approvals `KIND_MODULE` (`lib_approvals`) maps each SPEC 3.4 kind to the module whose `full` level may decide it as an administrator; a new kind outside that list is decided by its resolved approvers only.
